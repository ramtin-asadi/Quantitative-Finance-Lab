Overview

Purpose

Quantitative Finance Lab is a project-based research and engineering portfolio in quantitative finance.

Each project is designed to show more than a final result. The goal is to demonstrate the full workflow behind a quantitative finance problem:

  • understanding the financial question;
  • developing the mathematical model;
  • implementing the method in Python;
  • working with real market data;
  • evaluating assumptions, diagnostics, and limitations;
  • interpreting results clearly;
  • extracting reusable code into a python package named quantfinlab.

The repository is therefore both a research notebook collection and a software-engineering exercise.

Design principle

The central design principle is:

The notebooks explain and implement the research; the library turns that implementation into reusable code.

A notebook is used when the goal is exploration, explanation, diagnostics, or interpretation. Library code is used when the logic becomes reusable enough to support another dataset, another market, or a later project.

This keeps the project honest: the library is not presented as a general-purpose finance library. It is a focused companion package for the workflows developed in the notebooks.

How each project is structured

A complete project usually contains the following parts.

1. Motivation

The notebook starts with the financial problem and explains why the topic matters in practice.

2. Mathematical setup

The relevant equations, assumptions, and model logic are introduced before the implementation.

3. Data and implementation

The notebook explains the dataset, cleaning steps, modeling choices, and implementation details.

4. Experiments and diagnostics

The project compares methods, checks assumptions, and studies model behavior using tables, plots, and diagnostic summaries.

5. Interpretation

Results are interpreted rather than only displayed.

6. Library implementation

The final section of each notebook applies reusable quantfinlab components to a secondary dataset, market, or workflow. This section is meant to show that the project logic can be refactored and reused, not only executed once inside a notebook.

Current project areas

The implemented projects currently cover four areas.

Fixed income

Yield curve construction, discount factors, forward rates, bond pricing, duration, convexity, PV01, key-rate duration, and duration-targeted laddering.

Portfolio construction

Walk-forward allocation, liquidity-based universe selection, expected-return estimation, covariance estimation, mean-variance optimization, regularization, transaction costs, turnover control, and performance comparison.

Risk analysis

Drawdowns, volatility, VaR, expected shortfall, VaR backtesting, stress testing, CAPM beta analysis, rolling risk behavior, and risk contribution.

Options and hedging

Black–Scholes pricing, put-call parity, quote filtering, implied-volatility solving, analytic Greeks, autodiff Greeks, Greek uncertainty, and hedging P&L analysis.

What belongs in quantfinlab

Code is moved into quantfinlab when it is useful beyond one notebook cell.

Examples include:

  • curve construction and bond-pricing utilities;
  • portfolio selection, estimation, and optimization helpers;
  • risk metrics and reporting functions;
  • options-pricing, implied-volatility, and Greeks routines;
  • plotting and diagnostics used across project sections;
  • shared validation, data-cleaning, and result-formatting utilities.

Exploratory code can remain in notebooks. Stable logic should move into the library when it improves clarity, reuse, or secondary-market implementation.

Data and reproducibility

Many financial datasets are large, licensed, or not suitable for direct redistribution. For that reason, raw data are generally not committed to the repository.

In future, the process of data will be made clearer:

  1. The notebook will specify the required data, including source, format, and expected location.
  2. A data-processing script will be provided to transform raw data into the required format.

Evaluation conventions

Projects use consistent evaluation ideas where possible.

For portfolio and strategy work, important metrics include return, volatility, Sharpe ratio, drawdown, turnover, transaction costs, and benchmark comparison.

For risk work, important diagnostics include VaR, expected shortfall, exception counts, backtesting tests, stress windows, contribution analysis, and regime behavior.

For options work, important diagnostics include quote filters, parity checks, solver success rates, pricing residuals, Greek consistency, uncertainty bands, and hedging P&L attribution.

NOTE: We implement everything maunually if it’s the first time implementing it, from the second time to more, we use library to don’t repeat long codes that have been shown in the first time.

Interpretation standard

The notebooks are intended to be readable research artifacts. A result table or plot is not complete until it is interpreted.

A strong result discussion should explain:

  1. the main pattern in the output;
  2. whether the result is expected or surprising;
  3. what assumption may be driving it;
  4. how it changes the financial interpretation;
  5. what limitation should be kept in mind.

This is especially important in the final library implementation sections, where the same workflow is applied to a secondary market or dataset. Those sections should not only show that the code runs; they should explain whether the transferred workflow behaves similarly, where it differs, and what that says about the model.

Disclaimer

This project is for research, education, and portfolio demonstration only. Nothing here is investment advice. Results depend on data quality, assumptions, market conditions, transaction costs, constraints, and implementation choices.
